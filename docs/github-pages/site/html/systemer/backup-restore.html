Backup og restore

Runbook for sikker backup, gendannelse og efterkontrol af GamMaSite-data. Production-databaser gendannes gennem den ansvarlige hosting- eller backupleverandør; Docker-kommandoerne nedenfor er til lokal udvikling og restore-test.

Det skal beskyttes

DataPlaceringRestore-kilde
ApplikationsdataSimply/MySQLProvider-backup eller lokal SQL-dump
Finance-dataNeon/PostgreSQLNeon-backup eller lokal PostgreSQL-dump
Content-mediaPersistent content-media-lagringCloudflare/backup-lagring eller lokal volume-backup
Schema Source of Truthsrc/database/Git og den valgte commit

Før database-deployment

  1. Kør diff, validate eller plan i Database schema management, og gennemlæs planen.
  2. Kontrollér database, environment og GitHub Environment, før et production-run startes.
  3. Bekræft, at den seneste provider-backup og content-media-backup findes og har en kendt timestamp.
  4. Ved MySQL skal der tages højde for, at DDL ikke er atomisk. En senere fejl kan derfor efterlade nogle statements anvendt.

Lokal backup

Kommandoerne køres fra repositoryets rod, mens de lokale Compose-databaser er startet. Gem backupfiler uden for repositoryet, eksempelvis under $env:TEMP\gammasite-backups.

$backupPath = Join-Path $env:TEMP "gammasite-backups"
New-Item -ItemType Directory -Force $backupPath | Out-Null

docker compose -f src/services/local-development/compose.yml exec -T mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers "$MYSQL_DATABASE"' > "$backupPath\gammasite-mysql.sql"

docker compose -f src/services/local-development/compose.yml exec -T finance-postgres sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=plain' > "$backupPath\finance-postgres.sql"

docker run --rm -v gammasite-local-development-content-media:/source -v "${backupPath}:/backup" alpine tar czf /backup/content-media.tar.gz -C /source .

Lokale databasevolumes og content-media-volume er separate. En almindelig docker compose down sletter dem ikke; down -v sletter dem og må kun bruges, når lokale data må nulstilles.

Lokal restore-test

Restore skal testes i et isoleret lokalt miljø eller en midlertidig database. Kontrollér først, at backupfilen ikke er tom, og at den ikke indeholder secrets, som skal deles.

Get-Content -Raw "$backupPath\gammasite-mysql.sql" |
  docker compose -f src/services/local-development/compose.yml exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'

Get-Content -Raw "$backupPath\finance-postgres.sql" |
  docker compose -f src/services/local-development/compose.yml exec -T finance-postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

docker run --rm -v gammasite-local-development-content-media:/target -v "${backupPath}:/backup" alpine sh -c 'tar xzf /backup/content-media.tar.gz -C /target'

Efter restore køres schema-validate, appens healthcheck, login, en offentlig indholdsside og relevante betalings-/finanslæseflows. Restore-testen dokumenteres med dato, backup-id og resultat.

Production-restore

  1. Stop eller begræns berørte skriveflows, hvis hændelsen kræver det, og følg beredskabsplanen ved kompromitterede data.
  2. Brug Simplys backup/restore for applikationsdatabasen og Neons backup/branch/restore-funktion for Finance PostgreSQL. Brug ikke de lokale Compose-volumes som production-backup.
  3. Gendan content-media fra den godkendte backup-lagring, og kontrollér at ContentMediaRootPath peger på den gendannede placering.
  4. Kør database-validering og en begrænset smoke-test, før normal trafik og skriveadgang åbnes igen.
  5. Notér tidspunkt, restore-kilde, berørte services, valideringsresultat og eventuelle manglende data.

Del aldrig dumps, connection strings eller backup credentials i issues, logs eller dokumentationen. En restore kan overskrive data og skal godkendes af den ansvarlige for det valgte environment.
