React API-reference

De JSON- og filbaserede API'er, som React-klienten bruger gennem src/frontend/services/api.js og src/frontend/services/financeApi.js. Endpointnavne og adgangskrav følger backendens aktuelle controllers.

Fælles regler

  • React sender same-origin credentials, så ASP.NET authentication-cookien følger med.
  • GET-kald kræver ikke antiforgery-header. POST, PUT og DELETE henter token fra /api/account/csrf-token og sender det som X-CSRF-TOKEN.
  • Multipart-upload bruger samme token i FormData. Filfelterne er angivet i de relevante rækker nedenfor.
  • Beskyttede endpoints kræver login og kan desuden kræve en permission eller arrangøradgang. Backendens autorisation er den afgørende kontrol; klienten skjuler kun funktioner i brugergrænsefladen.
  • Succesfulde kald returnerer normalt JSON. Handlinger uden payload kan returnere 204 No Content. Validerings- og adgangsfejl returneres typisk som 400, 401, 403 eller 404; rate-limited kald returnerer 429.

Ingen API-endpoints matcher søgningen.

Eksempler på svar

GET /api/me returnerer den aktuelle login- og rettighedstilstand. En autentificeret bruger får eksempelvis:

{
  "isAuthenticated": true,
  "id": "user-id",
  "userName": "medlem@example.org",
  "email": "medlem@example.org",
  "name": "Medlem Navn",
  "status": "BETALT",
  "roles": ["MEDLEM"],
  "permissions": ["content.edit"]
}

En anonym bruger får samme struktur med isAuthenticated: false og tomme arrays for roller og permissions. GET /api/account/csrf-token returnerer et objekt med feltet token.

DTO'er og testdækning

JSON-body'er følger DTO'erne i src/backend/GamMaSite/ViewModels/Api/. De vigtigste finansielle body-formater er angivet i tabellen ovenfor. Betalingscheckout skal have en unik Idempotency-Key pr. logisk checkoutforsøg.

Backendens tests ligger i src/test/GamMaSite.Tests/ og dækker blandt andet konto, content, editor, e-mailtemplates, finansvalidering, medlemmer, beskeder, betalinger, roller og eventtilmeldinger. Finance CRUD, PostgreSQL-konflikthåndtering, importhistorik, provider-matchning og fuld HTTP-autorisation kræver integrationstest mod en separat PostgreSQL-database.
