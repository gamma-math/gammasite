Database og schema-værktøjer

Databaselaget består af to source-of-truth-skemaer, en fælles Python-baseret schema-management CLI, test-seeds og et separat script til PostgreSQL-roller. MySQL gemmer den primære GamMaSite-data; PostgreSQL er den dedikerede Finance-database.

Arkitektur

SQL-filerne i src/database/ beskriver den ønskede databasestruktur. De er ikke kun installationsscripts: schema-værktøjet læser dem, sammenligner dem med live metadata og bruger dem til at danne en sikker, additiv deployment-plan.

Python-modulerne

Schema-management-koden er samlet i src/database/scripts/ og eksponeres som python -m src.services.database eller direkte via src/database/scripts/cli.py.

ModulAnsvar
cli.pyCLI-entrypoint med kommandoerne diff, validate, plan og deploy.
connections.pyFinder og parser databaseforbindelser, understøtter .NET connection strings og database-URL'er, skjuler passwords i logning og opretter read-only sessioner til kontrolkommandoer.
schema_reader.pyParser source SQL og læser metadata fra MySQL/PostgreSQL, herunder tabeller, kolonner, constraints, views, funktioner, triggers og indexes.
schema_compare.pySammenligner ønsket schema med live metadata og rapporterer forskelle uden at ændre databasen.
schema_deploy.pyDanner og udfører additive planer. Destruktive eller risikable ændringer blokeres eller kræver eksplicit --allow-risk.
src/services/database/Service-wrapper, requirements og lokal virtuel Python-environment omkring den fælles implementation; det er ikke et parallelt schema-system.

Arbejdsgang

  1. Redigér den relevante SQL Source of Truth og opdatér eventuelle test-seeds eller rolle-grants, hvis datamodellen ændres.
  2. Kør validate for at se, om en live database matcher source-filen. Kommandoen bruger en read-only session.
  3. Kør plan for at se de SQL-statements, som en additiv ændring vil generere, uden at udføre dem.
  4. Kør kun deploy --confirm, når planen er gennemgået. Produktion kræver desuden --confirm-production.
  5. Efter deployment sammenlignes schemaet igen. PostgreSQL kører deployment i én transaktion; MySQL-DDL committes statement for statement og kan derfor kræve manuel oprydning efter en delvis fejl.
python -m src.services.database validate --db mysql --env local
python -m src.services.database validate --db postgres --env local
python -m src.services.database plan --db mysql --env test
python -m src.services.database deploy --db mysql --env local --confirm

Lokal Docker-integration

Den lokale Compose-stack starter MySQL-servicen, Finance PostgreSQL og appen. Schema-værktøjerne kan køre fra værtsmaskinen med den lokale virtuelle environment eller i tools-containeren. Compose bruger interne servicenavne mellem containere; fra værten er MySQL normalt tilgængelig på port 3306 og Finance PostgreSQL på port 5433.

Seed-containeren indlæser kun testdata eksplicit og skal bruges mod tomme, lokale databaser. docker compose down -v sletter lokale database- og media-volumes og må derfor ikke bruges som almindelig stopkommando.

GitHub Actions installerer de samme Python-drivere og kører schema-validering mod Test eller Produktion før database-deployment. Connection strings kommer fra secrets/environment variables; credentials må ikke lægges i SQL-filer, .env eller dokumentationen.

Sikkerhedsregler

  • Brug diff, validate og plan før enhver deployment.
  • CLI'en genererer ikke automatisk DROP TABLE, DROP COLUMN eller data-migrationslogik.
  • Indexes, constraints, views, functions og triggers kan kræve --allow-risk og skal vurderes manuelt.
  • Finance-roller og grants er eksplicitte. Tilføjes en ny Finance-tabel eller sequence, skal rolle-scriptet vurderes og opdateres samtidig.
  • Test-seeds må kun bruges i lokale eller isolerede testdatabaser; de er ikke en backup eller produktionsmigration.
